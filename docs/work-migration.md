# Work-machine handoff

Preparation runs on the home computer only. The user-supplied work archive is an old reference, not access to the work computer or a statement of its current configuration. Use it to design improvements for both environments, not as policy to restore verbatim. No work-PC installation or test is claimed from inspecting it on home.

## Keep the layers separate

- Shared: the selected twenty Matt skills and the same Pi adaptation/provenance, project resolver and common personal policy.
- Work-only: reviewed corporate skills, private bootstrap/instructions, project mappings, tracker choices and MCP/auth restrictions. The old archive contained twenty-four corporate skills; verify the current collection and applicable policy on the work PC.
- Machine-specific: final `~/.pi/agent/AGENTS.md`, paths, secrets and local state. Do not replace this with the home file.

The archived work Matt folder is named `matt`, not `matt-pocock`, and contains local per-skill corporate adapters. Regenerate from clean pinned upstream; do not promote those private additions into the public adapter. Discover actual directories on the work PC first and move only that known Matt collection to a backup outside discovery. Keep the separate corporate collection out of the common installer; review it separately rather than discarding or endorsing it based on age alone. Do not let both Matt collections load.

## Private global instructions

The machine-profile installer owns only its checksummed navigation block and preserves other existing text. Byte preservation is a safety mechanism, not endorsement of every old instruction. It cannot safely classify or relocate arbitrary legacy corporate rules. Privately inspect the existing global instructions before applying work: machine-wide security constraints may remain global; project-only corporate bootstraps/rules should be referenced by the selected work project profile, not imposed on personal projects merely because the PC is at work. Preserve originals and review any private refactor locally; never put their contents in this repository.

`profiles/work.projects.example.json` is only a starting example, not verified corporate policy. Set the actual private personal/work rules and tracker settings in `~/.pi/agent/projects.json`. The shipped example uses a neutral personal/local fallback and selects work only through an explicit synthetic corporate namespace rule that must be replaced with the actual private rule. It must not classify all repositories as corporate merely because this is a work computer; GitLab hosting alone is not a corporate selector. This fallback is not proof that an unresolved task is personal: use confirmed applicable private discovery pointers to find a corporate task's actual target, even when Pi starts elsewhere. Review or replace old bootstrap/map candidates before relying on them; their archived locations and blanket loading rules are not requirements of this design. Read existing repository standards in either profile. Do not infer tracker authorization from remote host alone.

## Verification checklist

1. Record actual versions, settings paths and sources, private file hashes and skill discovery before changing anything. Do not dump secret contents.
2. Back up global instructions and the known legacy Matt collection outside discovery. Compare the actual work state with the archive and revise any archive-derived plan for differences; do not overwrite newer state to match the archive.
3. Prepare the inherited private projects file without per-repository scaffolding; keep corporate instruction pointers outside Git. Missing optional personal notes need no setup run.
4. Plan/apply the common Matt collection and the work machine-profile block; retain a backup of private original text and preserve the independently reviewed corporate collection. Do not copy home auth, device identity or browser state.
5. Validate discovery: twenty common Matt plus the actual corporate collection, no duplicate names; validate project resolution for both a corporate and a personal repository without creating files in them.
6. Reconcile the accepted combined extension pins and production dependencies using [installation](install.md). Do not install an older partial PR branch or unavailable local-only commit.
7. Restart Pi and verify real native behavior, model aliases, MCP exposure and independent authentication. Test Telegram with its dedicated local profile and private current permissions only; do not restore archived test grants.

Archive equality, home tests and a version string do not prove steps 5–7 on the work machine. Keep their results in a private receipt, not this public configuration source.
